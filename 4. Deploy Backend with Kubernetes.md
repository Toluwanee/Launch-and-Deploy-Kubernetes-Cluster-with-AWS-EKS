### Container image

Once I cloned the backend code, I built a container image of the backend. This is because a container image lets Docker set up multiple, identical containers so your application runs consistently across different environments.
Without an image, it would be difficult for Kubernetes to do anything. Kuberenetes does not work with backend code directly, it works with container images that are already built from backend code.

I also pushed the container image to a container registry, which is safe and stored containers securely... ECR facilitates scaling for my deployment because it's an AWS service, which lets Elastic Kubernetes Service (EKS) deploy your container image with minimal authentication setup.

## Manifest files

Kubernetes manifest is a set of instructions that tells Kubernetes how to run your app. Kubernetes uses it to know what your app needs, like which containers to run, how many copies to create, and how much memory to allocate.

This is why manifest are useful.
Without manifests, Kubernetes wouldn’t know how to set up and manage your app automatically. You'd have to manually configure each container every time you deploy, which would be confusing, error-prone, and hard to repeat. Manifests make deployment much more simple and consistent.

A Deployment manifest tells Kubernetes exactly how to manage tasks like creating and replacing groups of containers, scaling your app, and rolling out updates.
The container image URL in my Deployment manifest tells Kubernetes where to pull the container image from when it deploys your application.




A Service resource exposes my backend using your node's IP and a port number. My Service manifest sets up Kubernetes to create or update that traffic controller. In it, you list which pods to target, the kind of traffic to accept, and the ports to listen on.

## Verifying Deployment

My extension for this project is to use the EKS console to visually inspect my cluster's active node groups, view individual nodes, and verify the runtime status of my deployed pods in real-time.

I had to set up IAM access policies because Amazon EKS is secure by default. Even if an IAM user has full AdministratorAccess inside AWS, the Kubernetes control plane does not automatically grant that user visibility into nodes or cluster workloads without an explicit mapping.

I set up access by running an eksctl command to create an IAM identity mapping. This mapped my personal IAM User ARN directly to the Kubernetes system:masters group with administrator privileges, bridging my AWS credentials to the cluster's internal RBAC system and allowing me to view my nodes in the console.

Once I gained access into my cluster's nodes, I discovered pods running inside each node. Pods are the smallest, most basic deployable units in Kubernetes that you can create and manage. A pod represents a single running process in your cluster and hosts one or more tightly coupled containers that need to work closely together.

Containers in a pod share the same network namespace (including their IP address and port space, allowing them to communicate over localhost), shared storage volumes, and container specifications, running together on the same virtual or physical node.

The EKS console shows you the events for each pod, where I could see the live lifecycle logs of my deployment - specifically tracing how the pod transitioned from image-pulling failures to successful "Pulling", "Pulled", "Created", and "Started" container events once I updated the manifest with the correct ECR image URI.

This validated that my EKS cluster was successfully authenticating with my private Amazon ECR repository, and that my node group had successfully scheduled and launched my backend pods in a healthy "Running" state.
